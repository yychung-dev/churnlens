## M0|環境建置與資料載入

### [M0-1] 結論：`data/raw/` 不進版控，README 附下載指引。

- 理由一：公開資料集再散布屬授權灰色地帶，附取得指引是資料社群通行做法。
- 理由二：「不隨意複製散布資料」是資料治理意識。
- 理由三：保持 repo 輕量，clone 快速。
- 否決替代方案：「直接 commit CSV (方便 clone 即用)」，便利性不足以抵銷上述三點；可重現性改由下載指引 + 載入腳本保證。

### [M0-2] 結論：版控採 main / develop / feature 三層流程；feature 完成先進 develop，模組驗證標準全數通過後才由 develop 進 main。

- 理由一：main 必須隨時保持「觀看者任何時刻點進來都是完整穩定而非半成品的狀態」，需要 develop 作為整合緩衝層。
- 理由二：三層流程與業界多人協作慣例一致，單人專案沿襲此工程紀律，不只追求最小可行的版控。
- 理由三：「確認無誤」的明確定義是，merge 進 main 時，該模組驗證標準全數通過 + 補齊決策日誌。
- 否決替代方案：「簡化 feature branch(feature 直接 merge main)」，失去整合緩衝，以標準流程保證 main 的穩定性。
- 補充：merge 一律 `--no-ff`，保留各模組分支的歷史結構，使 commit 圖可讀出專案的模組化開發節奏。

### [M0-3] 結論：資料一律分層：檔案系統分 `data/raw/` 與 `data/processed/`，資料庫分 `raw` 與 `clean` schema；原始層資料唯讀，所有清洗加工都只寫入新的分層。

- 理由一：可追溯，任何分析結果被質疑時，能從原始層重跑整條清理流程，定位問題出在哪一步。
- 理由二：可重現，「原始資料 + 清理腳本 = 分析用資料」成立，任何人都可重建 clean 層。
- 理由三：此即資料工程 staging 概念的縮影，與後端「不直接改 prod，要以 migration 留下變更紀錄」的精神相通。
- 否決替代方案：「單層，直接在原始資料上清理」，雖能省一次複製流程，但清理是有破壞性的操作，若出錯就不可逆，喪失『原始真相』的原點。

### [M0-4] 結論：raw 層所有欄位用 TEXT 型別，不在載入階段做任何型別轉換。

- 理由一：載入永遠不會因型別問題失敗(髒值、格式異常照單全收)，重點在「資料能進來」。
- 理由二：raw 層的職責是保留原貌；型別轉換本質上是一種清理，應在 clean 層明確決策、執行並留下紀錄。
- 理由三：M1 稽核時才知道每欄真實的髒法，若現在先定型別，是在資訊不完整時就做不可逆的假設。
- 否決替代方案：「載入時直接定義正確型別」的狀況有兩個問題，(1)若任一列有髒值就會導致整批載入失敗；(2)把資料清理混入資料載入流程中，是違反分層架構原則([M0-3])。

### [M0-5] 結論：PostgreSQL 容器不掛 volume，容器刪除即清除資料，停止/重啟容器則不影響。優點：資料隨時可依 CSV + 腳本重現，資料可重現性由自動化 pipeline 腳本保證，不由容器狀態保證。

- 理由一：本專案真實資料隨時可由 raw CSV + sql/ 腳本重現，資料庫隨時都能以三條指令在 15 分鐘內重建，符合 M0 驗證標準「砍掉容器就能重建」。
- 理由二：所有變更都寫在有版控的自動化 pipeline 腳本裡。不依賴容器內部狀態，也避免「在資料庫手動修改」的情形，保證專案在任何電腦執行都有相同結果。
- 否決替代方案：「掛 volume 持久化」，這是多人或正式生產環境的正確做法。本案是單人分析的環境，重點是「自動化腳本的維護」，不是依賴資料庫的存檔。
- 2026-07-21 實證：Docker Desktop 關閉導致容器停止，docker start 即可復原 (將既有容器重新開機，並經 SELECT指令 驗證原資料仍完整存在)；即使容器被刪，README 路徑可於 15 分鐘內重建。本則決策所承諾的可重現性，已經真實案例驗證。

### [M0-6] 結論：依然在 raw 層載入「陷阱一的兩個欄位 (模型輸出欄)」(改成較短名稱如 nb_classifier_prob_1)，刪除這兩欄的動作留給 clean 層執行。

- 理由一：維持「raw 層保留原貌」的原則([M0-3])，「這兩欄該刪除」屬資料清理的決策，應發生在 clean 層並記錄理由。
- 理由二：縮短欄名是安全的，因為 \copy 語法是「按欄位位置對齊」，與欄名無關；且原始欄名(Naive*Bayes_Classifier*...)過長、難閱讀，將其改短是為了提升「開發的可讀性」，不改動資料內容。
- 理由三：保留這兩欄，明確呈現「data leakage 的處理」，在 raw 層看得到這兩欄 → 在 clean 層刪除這兩欄 → 在日誌記錄刪除理由，形成完整的稽核軌跡。

### [M0-7] 結論：批量載入原始資料採 `\copy` + 手寫 DDL；M1 起 Python pipeline 寫回 clean 層採 pandas `to_sql`。依不同層 (raw、clean) 的職責選擇不同工具： raw 層的核心價值是「人工審核資料的載入，防止髒資料破壞結構」，clean 層的核心價值是「與 Python 清理流程自然整合」。

- 理由一(型別控制)：`\copy` 進全 TEXT 表，不做型別轉換，型別決策延後到稽核之後(M1)的 clean 層才明確執行；`to_sql` 由 pandas 自動推斷型別，導致髒資料在未經稽核前被盲目定義型別。實測佐證：同一份 CSV 兩種方式各載一次(筆數皆為 10,127)，`information_schema.columns` 確認 `\copy` 版 `customer_age` 為 `text`、`to_sql` 版為 `bigint`。
- 理由二(控制資料載入方式)：M0 實測發現 `to_sql` 的自動化不只發生在型別，欄名長度、欄名大小寫也直接依照 CSV 原始格式，兩者都造成真實問題(詳見 [M0-Issue1]/[M0-Issue2]：63 字元截斷導致建表失敗、大寫欄位名導致後續查詢漏抓資料)。`to_sql` 自動化載入的每一個環節：欄位名、大小寫、型別都未經人工審核而出錯，**用 `\copy` + 手寫 DDL 則能自己控制資料依正確方式載入** 。
- 理由三(效能與可擴展性)：`\copy` 走 PostgreSQL 二進位資料流通管道，不經 Python 轉換；`to_sql` 則需經 Python 將資料逐批拆解並組裝成龐大的 INSERT 字串。資料量大時兩者的載入速度可相差高達數十倍，可能造成效能瓶頸。雖本案只有 1 萬筆資料時感受不明顯，但考慮可擴展性，raw 層載入應優先選擇效能好的`\copy` 方法。
- 理由四(to_sql 的正確應用)：clean 層與後續小結果表(如 M5 分群預測結果)本來就以 Python DataFrame 的形式存在，用 `to_sql` 寫回資料庫最自然；且前面已在 Python 中把資料型別整理好，此時讓 pandas 自動推斷型別反而是優點，省下手寫建表指令的力氣。
- 代價(多寫 DDL 的代價)： `\copy` 需多花時間手寫 DDL 腳本建立空資料表，且從 raw 轉換到 clean 層時需在 SQL 裡一個欄位一個欄位手動寫出轉型別語法。但優點是「每行轉型別的規則和邏輯都會被清楚記錄，方便追溯與查核」。
- 否決替代方案一：「全程用 `to_sql`(含載入原始 CSV 檔)」，等於把欄位名、大小寫、型別的決定權交給 pandas 自動推斷與處理，「把控制權交給工具猜測推斷」對髒資料而言不安全；且大資料量情況下`to_sql`效能不佳、速度慢；M0 實測更因欄位名問題導致建表失敗。
- 否決替代方案二：「全程用 `\copy`(含 clean 層寫回)」，clean 層已用 Python 算好乾淨結果存在 Python 記憶體中，若要用 `\copy` 寫入資料需先把資料存成 CSV 再載入，多一次中介檔案與人為操作步驟。對已處理且可控的資料直接用 `to_sql` 寫回去就好，沒必要繞遠路用 `\copy` 。

### [M0-Issue1] 因 PostgreSQL 欄位名過長，pandas `to_sql` 發生字元截斷，導致欄位名衝突。

- 現象：`to_sql` 寫入時報 `DuplicateColumn` 錯誤，問題點在「自動生成的 CREATE TABLE」。
- 成因：CSV 末兩欄原始欄位名約 130 字元，只有末尾的(`_1`/`_2`)不同；PostgreSQL 的欄位名長度上限為 63 bytes 因此自動截斷超過的字元，截斷後兩個欄位名完全相同，進而發生欄位名稱相同的衝突報錯。
- 解法：寫入前將末兩欄改名為 `nb_classifier_prob_1/2`(比照 `00_ddl.sql` 的人為決策)。
- 收穫：`\copy` + 手寫 DDL 不會出這種錯，原因是「欄位名在 DDL 階段經過人為決策」，符合 [M0-7] 「人工審核決策」結論。

### [M0-Issue2] `to_sql` 直接依 CSV 原本的大寫欄位名套用，導致元數據（Metadata）檢索失效 (`information_schema` 比對查詢時漏抓資料)

- 現象：以 `column_name = 'customer_age'`(全小寫)查詢型別比對時，只回傳 `\copy` 版結果，`to_sql` 版則檢索不到。
- 成因：PostgreSQL 對未加雙引號的識別字 (Identifiers) 一律自動轉小寫，但 `to_sql` 以雙引號原樣建立 CSV 的 `Customer_Age`(大寫)，全小寫條件因此比對不到大寫的欄位名。這類欄位將來每次查詢都必須寫 `"Customer_Age"` (帶雙引號)，一旦缺少引號就報「欄位不存在」錯誤。
- 解法：比對查詢改用 `LOWER(column_name) = 'customer_age'`；治本的預防作法是「遵守識別字一律 snake_case 小寫的慣例」(手寫 DDL 已遵守此慣例，但 `to_sql` 不會自動把關)。
- 收穫：`\copy` + 手寫 DDL 靠人為決策把關，不會出這種錯，但 `to_sql` 自動化不會為這種命名慣例把關。

備註： DDL（Data Definition Language）是「定義資料庫骨架與結構」的 SQL 腳本。

### [M0-8] 結論： 資料庫連線設定改由 .env 管理 (python-dotenv)，搭配 fail-fast 驗證與 singleton engine；程式碼中不保留任何連線的預設值 (eg. 資料庫密碼、資料庫連線網址)。

- 理由一：secrets 與程式碼分離是基本資安意識。.env.example 進版控作為設定範本，實際的 .env 納入 .gitignore。
- 理由二：採取 fail-fast 策略可降低除錯成本： 讓錯誤在 import 時就立刻浮現並附修正指引，而非等到連線時才失敗。
- 理由三：singleton 設計模式，確保整個專案只建立一個 engine。create_engine 內含連線池 (SQLAlchemy 在底層會自動啟動一個連線池管理員，預設容納 5 條連線的連線池)，若沒用 Singleton，每次呼叫 create_engine 都會在記憶體中建立一個新的連線池，多次呼叫就會重複建池，吃掉過多沒必要的連線資源。
- 否決替代方案：「直接把密碼寫在程式碼中 + 環境變數覆寫」雖能提升本機操作的便利性 (在沒設定 .env 時可自動使用預設值，且理論上線上環境可用環境變數「覆寫」掉預設值來做對應操作)，但這種便利性會讓開發者產生惰性，導致測試密碼留在版控中；而且，「將密碼與程式碼分離」是基本的資安紀律，不應依風險高低而妥協，所以本專案決定不在程式碼中留存密碼預設值。
- 影響：README 的重建流程新增一步 `cp .env.example .env`。

> 註一：金額欄一律使用可容納小數的型別 (Pandas 用 float64、PG 資料庫自動 mapping 成 DOUBLE PRECISION) (細節見註 3)
> (1)資料型別的訂定應反映欄位語意的可能範圍 (金額的業務本質是可以「有小數」的，不因樣本剛好無小數而限縮在整數型別；且稽核D雖在min、max、avg都得出整數，但可能有某些資料是小數，但計算 min、max、avg 時剛好都算出整數，除非對每一格都做嚴格的正則檢查是否無小數)
> (2)避免發生 astype 無聲截斷 (Silent truncation)(eg.在大多數 Pandas 版本與標準 Numpy 路徑下，可能在對 50.5 這種含小數的浮點數執行 astype("int64") 時，使用 truncate 向零取整成 50 且不報錯)

> 註二：稽核檔皆使用 numeric：較嚴謹 (E 區需精確到和 0.01 相比)、本案不影響效能 (極大量資料的統計運算時，效能才可能被影響。本案資料表不大，幾乎無效能差異)、一致性(在不影響效能的情況下，整份檔案都用 numeric 轉，具備一致性及可讀性)

> 註三：若用手寫 DDL 建表，金額欄慣例選 NUMERIC (精確十進位)；本專案做法是經由 to_sql 自動 mapping 所以落地為 DOUBLE PRECISION，雖不及 NUMERIC 精確，但 DOUBLE PRECISION 的精確度對分析情境的效果與 NUMERIC 相同，所以可接受。因為：切片統計(平均、分箱)、檢定、建模等運算的結論精度需求在小數 2~4 位，而 float64 的誤差在第 15~16 位有效數字之後，所以誤差雖然存在但不會影響分析效果。本案用 NUMERIC 或用 DOUBLE PRECISION 所得出的結果、模型係數、報表都會相同。(用 NUMERIC 和用 DOUBLE PRECISION 效果會不同的情境：如「會計對帳」(上一筆交易逐筆加總後，要求分毫不差地對平帳目，而此時浮點誤差可能會被累積到在結果上能看出來的位數，就必須用 NUMERIC))。

### [M1-1] 結論：三個類別欄的 'Unknown' 保留為獨立類別，不轉 NULL、不剔除。

- 理由一：實測 Unknown 占比：education 15.00%、income 10.98%、marital 7.40%，占比量不低，若剔除將損失上千樣本，削弱 M3 檢定力。
- 理由二：「不願透露/未能取得」本身可能與流失行為相關，若直接剔除，概念等同「假設 Unknown 是隨機缺失 (MCAR, Missing Completely At Random)」，但此假設無法驗證 (因為資料裡沒有任何欄位解釋「為什麼這格是 Unknown」)；因此，保留 Unknown 資料，讓這樣的資料成為可分析的訊號。
- 理由三：轉 NULL 會使這些列在分組統計中，被聚合函數在「無任何警示或報錯的情況下，排除在計算之外」，如此，分母會在沒被察覺的情況下變小；因此，保留 'Unknown' 這個字串類別，能使每張報表的分母都如實包含全部 10,127 筆樣本。
- 否決替代方案：「剔除 Unknown 列」：原因如上；「眾數補值(mode imputation)」：因為 Unknown 佔比太大，且無理由相信 Unknown 是隨機缺失的情境 (有可能是「不願透露」的訊號)。若直接「把 Unknown 格填上該欄出現最多次的值」，等同「憑想像製造假樣本」，對占比達 10% 以上的 Unknown 直接做眾數補值，會嚴重扭曲該欄分布。

### [M1-2] 結論：clean 層職責定為「修正錯誤」，不預做分析取捨；分析上需排除的正確資料(avg_open_to_buy、months_on_book 等)於 clean 層仍保留，之後再由後續章節明確排除並記錄理由。

- 理由一：clean 層是所有章節共同依賴的基礎資料，M2 切片仍需要 avg_open_to_buy 與 months_on_book；不該單獨因為 M4 這章的建模需求，就直接在 clean 層刪除(不該讓 M4 單獨章節的需求直接決定全案的資料內容)。
- 理由二：在哪個階段用不到特定資料，就在哪個階段做「排除資料」的動作，並且在排除當下「註明理由」，將來閱讀時就能同時看見「刪除動作及刪除理由」。本例要在 M4 做特徵選擇時排除，就在 M4 排除並記錄於該處，在同一層做決策和註明理由。
- 否決替代方案：「在 clean 層就直接刪除分析上有疑慮的欄」：這個動作不可逆(因為後續章節都以此 clean 層資料為基礎，若此處就刪除，後續章節直接無從判斷取捨和分析)，而且「資料錯誤」與「分析取捨」是兩種性質不同的決策，本案由 clean 層專門處理「資料錯誤」，「分析取捨」則由後續章節來做，才不會混淆。

### [M1-3] 結論：nb_classifier_prob_1/2 於 clean 層刪除。

- 理由：(1)此兩欄是上游原作者的模型輸出。原作者以本資料集訓練過一個預測流失的模型：訓練時，「attrition_flag(每位客戶的真實流失結果)」即為該模型逐筆根據相關特徵(features，如年齡、信用額度...)比對、預測後，最後用來校準自身預測結果的「答案(預測模型的標籤 label)」。原作者依前述特徵 + 標籤做完模型訓練後，得出該模型對這一萬名客戶的「流失預測機率」，並將此存回資料集，即為此兩欄內容。這兩欄的內容本質上是「看過答案(attrition_flag)後產生的猜測」，因此這兩欄內容與目標變數必然具高度相關性。若本案模型訓練時將這兩欄當成主要特徵，等同本案模型在訓練時間接偷看答案(data leakage)：本案模型會因其壓倒性的相關而依賴此兩欄、冷落真實行為訊號(如：不活躍月數、客戶年齡、信用額度等等特徵)，造成本案模型訓練/驗證階段評估分數虛高、卻無法泛化(generalize)到真實資料。此外，還有(2)部署問題：此兩欄只為這一萬人算過一次，真實世界的新客戶資料永遠不會有這兩欄，所以預測模型上線後甚至無法執行。這兩個問題都能單獨定性此二欄位是「資料汙染」而非有效特徵，符合 [M1-2] 定義的「錯誤」，故於 clean 層刪除。

- 完成「稽核軌跡 (audit trail)」(落實 [M0-6] 的設計)：raw 層可見兩欄 → clean 層刪除 → 本則日誌記錄理由。

### [M1-4] 結論：新增欄位(Boolean)「目標變數 is_churned(= attrition_flag = 'Attrited Customer')」，原欄位保留；pipeline 以三道 assert(筆數 10,127、主鍵唯一、流失率 16.07%)把關，任一關失敗就中止寫入資料庫。

- 理由一：Boolean 欄讓全案口徑落實為資料結構，AVG(is_churned::int) 就是流失率，避免發生「各章節各自定義流失率時，每次都重新用字串比對 (attrition_flag = 'Attrited Customer')，可能因打錯字等瑕疵發生計算錯誤 (而且程式不會報錯)，造成各處口徑不一致(口徑漂移 Metric/Definition Drift)」的風險。
- 理由二：assert 把問題定義書的「口徑定案」從「寫在文件裡的約定(無強制力)」變成「程式每次執行都自動檢查的規則(由程式自動檢查，避免人為疏失)」。如此，若未來更改清理邏輯時不小心動到口徑(例如：有人擅自更改已流失客戶的定義)，那算出的 is_churned 為 True 的比例就會與原本算好確定的 16.07% (定義在 validate 函式中)不同，就會發生 AssertionError → 程式中止 (pipeline 報錯)，透過這個檢查方式發現問題。(但若該口徑的更動是正式決策，流程就是：改問題定義書 → 記決策日誌 → 更新 validate() 裡的常數 → pipeline 恢復通過)
- 保留原欄：attrition_flag 是原始事實，is_churned 是衍生欄位；衍生欄位隨時能由程式重新算出，但原始欄一旦刪除就無法彌補。

### [M1-5] 結論：age×tenure 相關係數以 SQL 實測為 0.7889，取代網路社群流傳說法(0.79–0.97 不等，常見引用 0.97)作為全案依據。

- 影響一(M4)：0.79 的共線性仍足以使迴歸係數不穩，維持「二擇一」決策不變。
- 影響二(M2)：較 0.97 情境放寬：tenure 存在獨立變異，可謹慎用於切片，判讀時明示「帳戶年齡(tenure)與年齡混淆」的這個限制。
- 分析方法的原則：對任何未經官方文件證實的資料集特性，以自己的 SQL 實測為準；本次實測否定了最常被引用的數字，即體現這個原則的價值。

## M2|EDA 與流失切片

### [M2-1] 結論：切片分析由「假設樹」驅動：九項假設(H1–H9)於任何切片執行前事先指定並定案；未立假設的欄位列為「次要檢視清單」，切片時順帶檢視，但不對「所有欄位逐一兩兩組合、全部做一次交叉切片」，而是「由先立的假設引導，只對單變數表現最強的 3–4 個維度做交叉切片」。

- 理由一：19 個屬性的可能切法達上百種，若無事先以假設引導的切片，概念等同「事後撈取」；依顯著門檻的定義(α=0.05 代表無真實差異時，每 20 次比較中平均仍有 1 次是偶然顯著)，若大量切片，機率上必然出現一些「純屬抽樣運氣的差異」，無法從結果本身分辨真假。
- 理由二：「假設」在「事前指定」是 M3 檢定對 p-hacking 的主要防線；假設樹的 commit 時間早於所有切片結果的產生時間，「先假設、後切片」的時間順序可由版控證明。
- 理由三：假設分「行為假設(枝 1–3，可介入)」與「結構假設(枝 4，不可介入)」兩類，前者供後續挽留方案據以設計，後者用於資源分配。概念：「假設的分類」為後續章節(M5 的方案設計與資源分配)預作準備。
- 次要檢視清單的取捨：education_level、dependent_count、marital_status、card_category、customer_age、credit_limit 未立假設。
  - 原因：1.缺乏明確的業務邏輯可據以預期方向(如：教育程度與流失沒有直觀的因果關係)，或2.受既有限制約束(card_category 受小樣本限制：card_category 切出來 Platinum 那格只有 20 人，差異再大也不可信 [稽核 B]；customer_age 與 tenure 混淆：兩者相關係數 0.7889，customer_age 切出來看到的「年齡差異」可能是「tenure 差異」造成的誤會 [M1-5])。<br/>
  - 綜上所述，單獨立假設、單獨解讀的意義有限。因此，在「次要檢視清單」順帶檢視即可，若順帶檢視發現有異常，就標記為事後發現(探索性發現，exploratory finding)並記入日誌，從嚴解讀；若進入 M3 檢定，報告中須明示其為事後發現、非事前假設。
- 否決替代方案：「對所有欄位逐一切片，再從結果中挑出顯著者」：每多一次比較，就多一次偶然顯著的機會，據此挑出的「發現」無法與「純屬抽樣運氣」區分；且被挑出的假設是看完資料才產生的，若再以同一份資料檢定即為循環論證，無法在 M3 主張「假設」為「事前指定」。

### [M2-2] 結論：單變數(單維度)切片依欄位性質分三種切法:類別欄直接分組(B1)；低基數整數欄(僅 6–7 種值)逐值分組、不分箱(B2)；連續數值欄 NTILE(5) 等量分箱、附各箱實際範圍(B3)。全檔輸出格式統一為 grp / n / churn_pct / diff_pp。

- 理由一：分箱是當「數值種類多到無法逐一檢視」時的trade-off；低基數整數欄逐值分組即可完整呈現，若套用分箱，會把不同值混入同一箱，喪失逐值變化的解析度(如 H2 需要看 0→6 每一格的走勢,觀察「逐月變化的曲線形狀細節」)。
- 理由二：連續數值欄採等量分箱而非等寬分箱：本案金額類欄位資料分布右偏([稽核 D])，等寬分箱會使多數樣本集中在前幾箱、尾端箱樣本稀少，各箱流失率失去比較基礎 (等寬分箱的每箱金額範圍整齊，但各箱人數差異懸殊，喪失各箱族群流失率的可比性)；等量分箱保證每箱約 2,025 人，比較基礎一致。(「比較基礎一致」指：流失率的可靠度取決於分母大小，分母愈小、流失率愈易受隨機波動影響；等量分箱使每箱樣本數相同，各箱流失率的可靠度一致，不會出現「可靠箱與雜訊箱混在同一張表」的問題)
- 理由三：輸出格式統一，n (樣本數) 永遠呈現在表格上, 判讀時樣本數與流失率同時可見，才能在每一張表上執行「小樣本規則(如 Platinum n=20 就不下結論)」。
- 已知限制：NTILE 依筆數均分、不管值是否相同，同值客戶可能被切進相鄰兩箱。實測影響：total_trans_ct 最高頻率出現同值的該數值樣本數僅 208 人，箱界模糊度有限，故五分位判讀可信；avg_utilization_ratio 零值人口超過一箱容量(溢入第 2 箱)，第 1/2 箱邊界模糊, 故此欄改以「0 vs >0」二分切片重驗(見 [M2-6])。

### [M2-3] 結論：切片結果的證據強度分「四級判定(強支持/支持/弱訊號/無訊號)」，判斷標準是「假設的關聯方向(正相關或負相關)是否命中預期 × 與基準流失率的差距幅度(diff_pp) × 資料分佈曲線形狀 × 樣本數」四項綜合；各級對應不同處置決策:無訊號者不再深究；弱訊號者記錄形狀但不進 M3 檢定；支持與強支持則列入候選洞察。

- 理由一：切片產出十餘張表，若無統一判斷標準，逐表的取捨會無客觀標準與證據、流於個案感覺；四級判斷標準讓「哪些進檢定、哪些不進」有可檢視的依據。
- 理由二：弱訊號不進檢定的依據:檢定次數愈多，偶然顯著的累積風險愈高(多重比較成本)([M2-1] 理由一)，檢定名額應留給「確認為真就能行動」的訊號；弱訊號即使確認為真也難以轉為行動，就沒必要佔一個檢定名額(CP值低)。
- 弱訊號實例應用：H7(收入)判定弱訊號、不進檢定:全距僅 3.85 個百分點，且 U 型的兩端(高收入與低收入)流失成因高機率不同，一份挽留方案無法同時對應這兩種族群，即使假設檢定通過也無法轉為行動；將「中等收入最穩定」的形狀留作 M5 資源分配參考。無訊號實例應用：婚姻狀態、扶養人數、客戶年齡，曲線平坦貼近基準流失率，此維度無法區分高低風險客群，不再深究。
- 「事後發現」實例應用：教育程度僅最高學歷端偏高(突出主體 Doctorate 21.06%、+4.99 個百分點、n=451 ; 弱訊號 Post-Graduate +1.76 僅作旁證(diff_pp 幅度小),其餘四級平坦於 15.20–15.94%,貼近基準流失率。非「學歷越高流失率越高」的整體單調趨勢),依 [M2-1] 流程標記為事後發現、從嚴解讀。

### [M2-4] 結論：對「官方未提供計算公式」的欄位建立證據等級管理:欄位定義分「已驗證/推斷」兩級；凡成為候選洞察主角的欄位，其定義必須以 SQL 實證升級為「已驗證」，無法驗證者維持「推斷」並於判讀從嚴。

- 執行紀錄一：avg_utilization_ratio 原依社群說法推斷為 total_revolving_bal / credit_limit。H5 列入候選洞察第 3 順位後觸發「證據驗證升級條件」，比照稽核 [E] 的驗證方式實測(容差 0.001，取該欄最小刻度)，結果：mismatch = 0，全數 10,127 筆吻合 ➡ 「此計算公式的定義」實證成立，H5 的商業解釋(額度動用率 0 = 零循環欠款 = 無財務綁定)取得可靠依據。
- 執行紀錄二：total_amt_chng_q4_q1 依欄位名推斷為 Q4/Q1 消費金額比值，但 Q4 與 Q1 的原始金額不在資料集中，無法驗證，證據等級維持「推斷」，H3 判讀應保守。兩欄的驗證狀態差異將載明於 README 資料說明區。
- 理由：判讀的可信度應受限於「對欄位含義的掌握程度」(判讀的可信度取決於「對欄位定義的掌握程度(上位概念)」以及「計算是否正確(根據上位概念執行計算)」)；明文分級「欄位定義是推斷還是已驗證」，可防止推斷在多次引用後被誤當成事實。

### [M2-5] 結論：H6(客服聯繫次數)定位為「風險標記」而非「提前預警」：訊號本身是全案最強(0→6 次完整單調，1.75%→100%)，但「能否根據此訊號提前示警」仍有疑問，此判斷須有所保留，列入 M3/M8 方法限制。

- 理由：「聯繫多」與流失的關係存在兩種解釋：(a) 服務摩擦累積導致流失(前兆)；(b) 已決定流失者辦理註銷、爭議、餘額處理而產生大量聯繫(結果)。本案資料為單一時點快照，無法區分「每次聯繫發生在流失決定之前或之後」；6 次組 100% 全數流失的「完美」數字反而可能偏向解釋 (b) 的痕跡。
- 處置：仍可作為風險標記來使用(一樣可依此圈出名單)；但「發現此訊號時，距離客戶實際流失還剩多少可介入的時間」無法依本切片的資料判斷並做決策，必須在 M3 檢定與 M8 報告明示此限制。
- 價值註記：此為「訊號強度」與「訊號可行動性」分離的案例：與 H8(統計顯著但實務意義小)互為對照，兩者共同構成 M8 敘事中「不高估既有證據的效力(實際作用)」的素材。

### [M2-6] 結論：階段 C 交叉切片僅取四個訊號最強的變數(total_trans_ct、avg_utilization_ratio 以 0 vs >0 二分、total_relationship_count、contacts_count_12_mon)兩兩交叉，共 6 組；不對所有變數都做交叉。

- 理由一：兩兩配對的組合數隨變數量呈平方級(O(n^2)複雜度)成長(配對數:C的n取2 ➡ n(n-1)/2)，對所有變數都做交叉會產出大量無實質分析價值的表；只取單變數證據最強(訊號最強)的四個變數，讓交叉的每一組都有明確的驗證目的。
- 理由二：未能進入交叉切片的其他變數有其他安排：months_inactive_12_mon 與 total_trans_ct 同屬活躍度水位面向，「衡量同一面向的變數」互相交叉所得的資訊量低，所以取 total_trans_ct 為交叉切片變數代表；total_amt_chng_q4_q1 屬「變化方向」類的訊號，其任務(驗證 H1 的 Q2>Q1 假說)在階段 E 以分布比較處理，不佔交叉切片的名額。<br/>
  註：分布比較：並列比較兩組客群在該欄位的完整數值分布(直方圖/箱型圖)，而非只比平均數；若 Q1 與 Q2 的消費變化比分布形狀明顯不同 (eg.若Q2組的變化比整體明顯偏低，就支持「Q2是下滑途中的客群」這個假說)，即可驗證Q1和Q2這兩群人的性質不同(Q1客群雖交易筆數少但沒有下滑中、非流失前兆；Q2客群的交易筆數雖然比Q1客群交易筆數多，但消費下滑中表示Q2客群正在流失中)
- 理由三：階段 C 的兩個驗證目標:(1) 實測活躍水位類訊號的人群重疊規模(涉及挽留名單的去重、不重複編列挽留預算與客戶體驗)；(2) 檢視是否存在交叉後特別突出的組合客群，供 M5 挽留名單與 M4 特徵選擇參考。
- 附帶決策：H5 訊號以 0 vs >0 二分重驗(理由見 [M2-2] 已知限制)；credit_limit 的獨立性(是否為收入效應的影子)以「低額度 × 各收入組」交叉驗證(待驗證清單 #4)。

### [M2-7] 結論:交叉切片前,先依階段 B 的實測界線把四個訊號最強變數轉成二元旗標(低活躍 ≤61 筆、零動用 =0、淺關係 ≤2 項、高聯繫 ≥4 次),再以旗標做 2×2 交叉;消費下滑(<0.604)另設第五旗標,只參與交集人數量測。

- 理由:五分位對五分位交叉一組 25 格、每格約 400 人,必然出現大量小樣本格;二元旗標交叉一組 4 格,樣本數量有保障,且判讀重點(雙真格是否高於兩個單真格)最清楚。四條界線皆取自階段 B 的箱界或斷點,可作為 M5 名單圈選規則的第一版。
- 否決方案:1.五分位直接交叉(理由如上)、2.五個旗標全部兩兩交叉(共 10 組):比實作的 6 組多出「消費下滑 × 其他四旗標」的 4 張 2×2 表,而消費下滑的驗證任務(Q1/Q2 的分布比較)屬階段 E,這 4 張表不會改變任何後續決策,所以不需要多出的這4張表。

### [M2-8] 結論:零動用、淺關係、高聯繫三訊號與低活躍存在明顯交互作用:三訊號在低活躍子群內的組內差距(+9.2 ~ +60.5 pp)是活躍正常子群內(+3.8 ~ +7.5 pp)的 2.4 到 15 倍;低活躍是唯一具明確主效果的訊號。處置:三條洞察加註「風險效果集中於與低活躍同時成立的子群」;M4 評估納入交互項;M5 挽留資源聚焦低活躍子群。

- 理由:活躍正常子群在六張交叉表中對應的 12 格流失率(最高 9.58%)全部低於基準流失率 16.07%,對此子群獨立投放三份名單會把挽留成本花在低風險客戶上;此結論由兩條互不引用的計算路徑印證:路徑一為 C2 的比率比較(子群內組內差距的倍數差),路徑二為 C3-a 的人數分布(零動用名單圈到的流失者有 86% 落在與低活躍重疊側),兩者結論一致。
- 限制:觀察性資料只能建立關聯,無法確認因果,交互作用證明的是「訊號的影響幅度隨低活躍與否而不同」的關聯結構,不證明「低活躍導致其他訊號變得危險」。M3 的檢定報告與 M8 的簡報須明示此限制,不得寫成因果敘述;因果驗證交由 M6 的實驗設計。

### [M2-9] 結論:以四個正式旗標的命中數(0–4)做風險分層(流失率 1.34% → 98.67%,完整單調),作為 M4 模型必須勝過的簡單基準,以及 M5 名單分層的第一版;「至少命中一旗標」的名單(去重後 7,292 人,占全體 72%)不具篩選功能,不得作為挽留名單。
